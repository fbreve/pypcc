# Frozen experiment: does sklearn nearest-neighbor engine choice improve exact PCC graph construction?

**Preregistered before CI timing or outcome collection.** This is an independent observational experiment based directly on production `master` `8298ece05c4edf4bbdc871d0aa5b13d9b8ed4128`. It neither modifies `pcc_graph.py` nor incorporates unmerged CSR optimization #192, experimental trajectory #182–#188, or performance scripts #190–#191. Preserve #192 DRAFT until independently approved.

## Research question and disqualification rule

The measured original master/CSR candidate profiling in #191 showed that original `NearestNeighbors.fit(...).kneighbors(X)` is the largest kNN-graph construction stage for high-dimensional Digits. Does choosing a specific built-in exact sklearn nearest-neighbor search **algorithm** ever yield a reliable faster *whole-graph* builder while preserving the **entire original ordered, padded symmetric graph**?

The current source uses `NearestNeighbors(n_neighbors=k+1,algorithm="auto",metric="minkowski",p=2,n_jobs=1).fit(X).kneighbors(X,return_distance=False)[:,1:]`. Test **only** `algorithm="auto"` (frozen reference), `"brute"`, `"kd_tree"`, and `"ball_tree"`. An alternative is implemented by loading the **exact original master Git blob** and replacing **exactly that one algorithm string** in an ephemeral isolated Python module at runtime, with no other text or runtime modifications; hash the original and the replaced source and use the same graph builder for each, not an approximate CSR clone.

**Graph output, not raw sklearn neighbor rank alone, is the functional contract.** Alternative engines may disagree on tied or duplicate distances. For each condition compare the *complete* `neib_list` (including order, full `-1` padding, shape/dtype) and `neib_qt` arrays to unchanged `auto`. Always record whether equivalence holds and differences (count of mismatched rows, unexpected edges, missing edges). On adversarial tied inputs an alternative may be **invalid**; treat mismatches as a *reported* safety disqualification, not a reason to hide that condition or fail the descriptive study. The unmodified `auto` reference MUST be deterministic and match its own exact array fingerprint. No arbitrary tie-breaking changes to PCC are authorized.

## Prospective fixed cohort and measurements

- **2 independent CI OS runners**, `ubuntu-latest` and `windows-latest`, Python **3.12**; cap `OPENBLAS_NUM_THREADS=OMP_NUM_THREADS=MKL_NUM_THREADS=NUMBA_NUM_THREADS=1` to 1, `n_jobs=1` throughout. Record full `pip freeze`, installed sklearn/NumPy/SciPy versions and CPU model. Do not pool OS results or extrapolate to the local workstation.
- **Four original sklearn datasets**, `iris`, `wine`, `breast_cancer`, `digits`, globally standardized by original `StandardScaler`; **three k values 1, 3, 10** with original Euclidean Minkowski `p=2` and full production union-symmetrized CSR adjacency; exactly **12 dataset×k cases** per OS and **three alternate engines**.
- First collect one unmeasured warm-up per algorithm for each case, then **20 real alternating paired full original-vs-candidate builder repetitions per dataset×k×alternative engine**. For even repetitions run original `auto` first, for odd candidate first. All 20 observations retained including outliers and mismatches. Total **4×3×3×20 = 720 matched pairs / OS, 1,440 pairs both OS**, plus fixed warmups. Each repeat times the **whole original build** including nearest-neighbor fit, kneighbors, sparse symmetrization and ordered dense arrays. Require the reference output identical at every repetition.
- For each dataset×k×algorithm, record **actual sklearn `_fit_method` selected** (`auto` resolves to either brute/KD-tree/Ball-tree as it sees fit), complete source/graph SHA, raw query-neighbor differences versus the original `auto`, and **separate descriptive medians of nearest-neighbor fit and query phases** in **10 full `NearestNeighbors.fit` + `kneighbors(X)` iterations**, per engine (4×3×4×10 = 480 component measurements/OS). Warm the functions beforehand. These component timings are **not** the authoritative overall speed endpoint.
- **Preselected synthetic/adversarial fixtures**, never chosen based on performance: exact duplicated/tied rows in 2D, regular equal-distance grid, noncontiguous/Fortran-ordered numeric input, repeated constant feature rows, and a 1D chain with equidistant interior points. For each valid fixture compare original `auto` against all three engines at k=1,3,min(10,n-1), p=1 and p=2; explicitly record exact ordered graph equality (no failed case silently dropped). Report counts by engine of compatible/incompatible fixture×k×p conditions and a concrete first mismatch when one exists.
- **Complete native graph controls** only where alternative is graph-equivalent: for the 4 real datasets/k=10, one fixed class-balanced labeled mask per dataset (new seed **28109**), two native backends **Numba and Cython**, original `max_iter=1000,early_stop=False`, compare the original graph vs each equivalent candidate graph using the unchanged existing `benchmarks.runner.measure`. Must match all **six final state SHA256 hashes, native stop info and accuracy within backend/seed**. No cross-backend RNG equality. If a candidate graph differs it is **not** passed to the PCC native test; record `skipped_due_to_graph_mismatch`, not a fabricated passed result.
- Require comprehensive strict artifact/aggregate CI: 720 complete graph pairs, 480 components and the fixed synthetic case inventory **per OS**, plus every expected exact-equivalent native case or an explicit documented mismatch skip; complete `pip freeze` and input-array hashes. Required two-OS aggregate shows paired whole-build median and quartiles, per dataset/k, actual resolved `auto` method, and incompatible synthetic examples. The CI must **not** assert that a candidate is faster: performance regression and graph incompatibility are both genuine scientific outcomes, not infrastructure errors.

## A priori go/no-go decision

Recommend a **single alternate engine as a universal production replacement** only if it (a) produces identical full graph arrays on **every** real and synthetic condition on **both OS**, (b) improves the **paired median full builder by at least 5% on k=10 in at least 3 of 4 real datasets on EACH OS**, and (c) has **no worse than 5% paired median regression** on any of the 12 real dataset/k conditions on either OS. No post-hoc engine-specific dataset heuristics, input-size cutoffs or exception paths from this small exploratory cohort; those would require their own preregistered independent study. A candidate can be identical on all real inputs but fail synthetic tie cases; that is an unacceptable default replacement. If no engine passes these gates, **leave production `algorithm="auto"` unchanged** and archive the negative result.

This is a descriptive, limited sample of original sklearn exact search engines; no HNSW/FAISS/ANN approximation, altered graph topology, threads, stochastic paths, inverse neighbor lookups, self-neighbor semantics or silent tolerance on output indices. The fixed 1000-iteration native check is not evidence of convergence or generalization. Backends have independent RNG implementations; only same-backend reference-vs-candidate exact agreement is required.
