## Question and scientific interpretation

How much full-fit CPU might be attributable to original Numba *weighted greedy score construction, cumulative scan, and search*, when actual particle destinations, states, random draw calls and stopping are **held strictly identical**? #231's `p_grd` variation cannot isolate this because changing `p_grd` changes the actual trajectory. #232 verified no greedy-to-random fallback in its 162 normal corpus scenarios but fallback MUST remain implementable and cannot be assumed unreachable in general.

An **oracle tape** of actual original greedy events is generated OUTSIDE timings by running a full true Numba clone with integer/floating sidecar records. The tape contains for each actual greedy attempt its particle ID, current node, true active degree, actual computed original total (after any original inf-rescale), selected neighbor index, original uniform random sample when weighted and whether weighted or fallback; it contains no invented decisions. A separate source-derived **oracle replay** Numba clone skips only weighted scoring/CDF and retrieves the prerecorded total and decision. Crucially it STILL executes the original `np.random.random()<p_grd` branch and the original `np.random.uniform(0,total)` (or `np.random.randint(k)` on fallback), with a hard equality guard against recorded actual random output, so RNG consumption and every choice match the original. Its native dynamics, all eight result arrays and true stopping must match the original exactly.

This is NOT an implementable production algorithm: the replay needs a previously generated complete oracle tape of the answer. Comparing original whole-fit process CPU to oracle full-fit CPU is **hypothetical diagnostic sensitivity** (cost of a scoring path replaced by tape lookups and guards), NOT a measured attainable optimization, a mathematically strict upper bound, or a code GO. Extra tape memory costs are excluded from the CPU timer but MUST be reported. Never claim that the difference can be realized in a real standalone classifier, nor infer micro-instruction cycle counts.

## Frozen interpretation, no production decision

The contrast reveals only *what would happen if an oracle supplied exact original weighted choices and totals*; **any reported CPU saving is a counterfactual, not a safe realizable speedup**. No GO/NO-GO gate exists: even a very large apparent benefit would not justify an implementation that omits the real weighted calculation, because a future fit has no oracle tape. If no meaningful CPU difference or Windows sampling quantization dominates, report accordingly. Original class behavior, floating precision, seed and dense padded neighbor graph are preserved. Independently validate both native hosts, strict cross-host and prior-run parity, and 4-platform normal package regression on final scientific head. Close this scientific PR without merge after documenting results. New production code would require a distinct genuine algorithmic hypothesis and preregistered whole-fit CPU GO with exact state/RNG checks.
