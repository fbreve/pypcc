## Research question and honest limits

The original Numba kernel produces substantially different whole-fit CPU at `p_grd=0/.5/1`, including more expensive mixed paths on Digits kNN10, but those policies **change the native RNG trajectory, destinations and state**. Count actual branch outcomes so we can distinguish some sources of work (weighted greedy attempts, success, fallback, invalid neighbors, labeled/unlabeled destination updates, non-greedy ownership accumulation, accepted/rejected position moves) from the coincident variation in visited-node populations. Counts describe how often work is reached, **NOT its isolated cycles, latency, memory traffic, branch-misprediction rate, or causal CPU share**.

A Numba counter must observe every actual particle step without replacing the algorithm or introducing backend alternatives. The monitored original/natively-counted pair must produce bitwise-identical eight final arrays, true Numba MT19937 next sample, current complete stop metadata, original C/F node/distance/degree layouts and unchanged previous-fit ownership/invalid-seed rollback. Compare to matching earlier #231 original frozen output hashes wherever identical fixed-mode parameters are used. **Counter-enabled wall/CPU timing is scientifically inadmissible as performance evidence**: no timed counters, no original-vs-counted speedup percentages, no production GO/NO-GO.
