# Prospective measurement addendum — Windows native process CPU timer resolution

Committed after the first **infrastructure-blocked** CI attempt, **before rerunning and before any complete two-host verdict**. It does **not** change candidate source, datasets, seeds, current master, state/RNG/source/cache requirements, or any preregistered **25% warm-new-process / +30% cold compile / +5% hot regression / 32MiB** performance threshold. Linux's original first-fit data and stdout are preserved in the failed first run [42603924667](https://github.com/fbreve/pypcc/actions/runs/42603924667); no timing sample is silently deleted.

## Reason for the repair
On Windows the `time.process_time_ns()` process CPU clock has insufficient practical resolution for the **sub-millisecond second already-JIT-loaded** full PCC fit (real `fit_predict` CPU often rounds to exactly 0 ns); the original auditor incorrectly rejected such a valid fast hot fit as "missing timed native CPU". This happened on the very first Windows source-original Wine case *before any Windows compiled-cache candidate* was measured, so the Windows scientific corpus was **incomplete**. Linux completed its full original measurement, including genuine cache save and reuse. The original CPU-for-new-process comparison is unaffected, since compilation takes hundreds of milliseconds and is well resolved.

## Immutable-method adaptation
Keep the exact original first `fit_predict` CPU/wall **in the first and second fresh processes** and the second in-process native fit with six-array/RNG parity. The second fit's process CPU may legitimately read 0 ns on Windows, but its wall time must be positive; no GO calculation uses its short single-call CPU duration.

To measure the existing predeclared **"already-hot native CPU must not regress more than 5%"** criterion with sufficient resolution, **each of the same 48 new interpreters** additionally runs **one process-CPU timed batch of precisely 512 sequential seeded `fit_predict` calls on a prepared, identical native Numba model**. The model construction and graph setup happen before batch timing; no loop-level observers or array hashing happen inside the timer; after the batch, compare its final six arrays, original stop counters and *next native Numba RNG draw* against the original first call. Candidate/baseline use exactly the same model-reuse loop. Report per-call **batch CPU = total process CPU/512** only for the original already-hot regression gate. 512 calls yield roughly hundreds of milliseconds of CPU time on both OS, avoiding short clock quantization; do not compare single-call hot CPU across OS.

Original count of **48 truly independent fresh processes and 96 first/second complete native fits** remains as primary study; the amended protocol adds **48×512 = 24,576 repeated already-JIT-loaded native fit calls** solely for high-resolution *steady-state regression* checking. All data, including original single-call CPU zeros, are archived. The first new-process CPU, candidate cache hit, initial compilation overhead, all thresholds, state/RNG equality, and total disk cache budget are UNCHANGED. A source-only minimal production PR remains conditional on full original criteria and own independent 4-platform CI.
