## Distinct hypothesis after #219
Actual dynamic Numba Callgrind #219 counted 2.7–2.8% `numba_get_np_random_state` + 5.6–6.2% native `__tls_get_addr` instructions. This is NOT measured CPU time, and Numba's own `numba.cpython.randomimpl.get_state_ptr` marks the getter `readnone` and `nounwind` with an explicit comment explaining LLVM can hoist redundant calls. Thus a manual pointer reuse might be redundant or slow. Previous native random/greedy loop transformations #105–#121, row-max #213 and graph neighbor #214 were separately measured and rejected. Do not repeat them. This experiment tests exactly ONE new mechanism: **reuse the real Numba NumPy MT19937 state pointer for both sequential `np.random.random()` and `np.random.uniform(0.0,total)` calls in one valid particle**, leaving original `np.random.randint(k)` unmodified.
