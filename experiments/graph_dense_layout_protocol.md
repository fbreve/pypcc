## Question / frozen candidate

The completed current-master [cross-OS 216-fit benchmark #190](https://github.com/fbreve/pypcc/pull/190) showed original one-time kNN graph construction is often larger than a warmed compiled PCC fit when a *new* graph must be constructed. Current `pcc_graph.build_knn_graph` and `build_graph_from_edge_index` build an **ordered dense padded neighbor-list** from an already symmetrized CSR matrix using one Python-level `np.arange(d)` array per node and `np.concatenate` (even for zero-degree nodes). Hypothesis: eliminate those per-row Python array creations while preserving **the entire exact original graph output**.

**Frozen single change:** at both CSR-to-dense scatter sites, replace:
```python
col_idx = np.concatenate([np.arange(d, dtype=np.int64) for d in degrees])
```
with mathematical offsets using **one global vector** and the original CSR `indptr`:
```python
col_idx = np.arange(adj.indices.size, dtype=np.int64) - np.repeat(adj.indptr[:-1], degrees)
```
Only apply when there are edges; for zero edges preserve the existing empty vector. The existing `row_idx`, CSR symmetrization, output `np.int64`, degree counts, `-1` padding and original **CSR neighbor order** remain unchanged. The `num_nodes=0` original edge-index special case, including `(0,0)` return shape, is untouched; graphs with isolates retain original `(n,max(max_degree,1))` shape. If the new arithmetic does not actually improve whole graph construction, record the negative result and **do not merge**.

## Decision and scientific caveats

This is **one** narrowly scoped structural optimization, not a redesign of graph topology or neighbor searches. The benchmark identifies where cost resides; it does not prove that graph preparation *always* dominates when users reuse a graph. Fully identical `neib_list`/degree arrays preserve graph inputs and node neighbor ordering, while the native 48-pair test verifies original propagation state across all original backends for these exact fixtures. This does not guarantee arbitrary future versions, all optional sklearn metrics, or convergence after 1000 iterations. No p-values or universal CPU recommendation from GitHub hosted runners. Because even a strictly equivalent graph-layout change can affect performance differently on real machines, **only propose production merge if whole-builder gain is meaningful, reproducible on representative datasets and not accompanied by excessive regressions**. Keep draft/unmerged otherwise.
